# ルールの形式

> **状態**: 設計済み(確認待ち)
> **専門役の判定(CD-GDD-ALIGN)**: 見直し頻度が最小限(lean)のため省略
> **作成者**: ユーザー＋Claude(取りまとめ)＋専門役のサブエージェント
> **最終更新日**: 2026-11-23
> **関わる柱**: 柱1「札で考える」、柱2「3秒で試せる」、柱3「壊れても遊べる」

## Overview(概要)

ルールの形式は、遊び手がルール盤に並べた札を「1つのルール」としてまとめる形である。
この形があるから、組み立てたルールを保存して後でそのまま開き直せ、ボタン1つで対戦に渡せ、将来は文字列にして人に渡せる。
持つのは札の識別名と調整値だけで、名前や日付は持たない。
壊れたデータや知らない札が混ざっていても、読める部分だけを読んで止まらない(柱3「壊れても遊べる」)。

## Player Fantasy(遊び手の体験)

間接の体験。**「並べた札が、そのまま残る」**

昨日「うちの大富豪」と名前を付けて保存したルールを開くと、置いた札もつまみの数字も元のとおり卓に戻っている。
見えている札の集まりがそのままルールである(柱1「札で考える」)。将来の共有でも、同じ札の集まりがそのまま相手に届く。
なお、札の並び順は意味を持たないため保存しない(`design/gdd/rule-card-definition.md` 基本の決まり3)。

## Detailed Design(詳細な決まり)

### Core Rules(基本の決まり)

1. **ルールが持つ項目**は次の3つだけとする。

| 項目 | 内容 |
| ---- | ---- |
| 形式の版 | 整数。1から始める |
| 札の一覧 | 識別名と、名前付きの調整値の組 |
| 使えない札 | 知らない識別名とその調整値。原文のまま持つ |

   ルールの名前・作成日・元にしたルールは「10 保存と名前付け」、人数・席は「8 対戦の開始と席」が持ち、ルールの形式には含めない。
   これにより、名前が違っても札が同じなら同じルールと判定できる。

2. **調整値の名前は固定**する。識別名と同じく一度決めたら変えず、共通の一覧(`design/registry/entities.yaml`)に登録する。

| 札 | 調整値の名前 |
| ---- | ---- |
| ジョーカー入り(`add_jokers`) | `count` |
| 最初に並べる(`place_on_field`) | `rank` |
| パスで負け(`lose_on_pass_limit`) | `limit` |

3. **文字列の形は JSON** とする(保存・共有で同じ形)。例:

```json
{"format_version": 1,
 "cards": [{"id": "act_pass"}, {"id": "add_jokers", "params": {"count": 1}}, {"id": "deal_all"}],
 "unusable_cards": []}
```

   札の一覧は識別名を鍵にした対応表ではなく並びにする。JSON の対応表では重複した鍵が解析時に後ろの値で上書きされ、「1枚目を有効」の決まりを守れないため。

4. **読み込むときに一度だけ整える**(正規化)。順番は次のとおり。
   1. 版が古ければ、版の移し替えを行う。
   2. 知らない識別名は「使えない札」へ移す。実行部分には渡さない。
   3. 同じ識別名は1つ目だけを残す。
   4. 調整値を整える。欠けていれば既定値、知らない名前の調整値は捨てる、整数でなければ四捨五入、範囲外は範囲内に丸める、調整値を持たない札に付いた値は捨てる。
   5. 札が0枚でも正しいルールとして扱う(注意はルール盤が出す)。

5. **書き出すときの決まった形**: 札は識別名の順に並べ、調整値は既定値と同じでも省略せずにすべて書く。既定値を後で変えても、保存したルールの意味が変わらないようにするため。
6. **同じルールかどうか**は、決まった形で書き出した文字列の一致で判定する。置いた順番に左右されない。
7. **安全のための決まり**:
   - 受け取った文字列はデータとしてだけ読む。Godot の資源ファイルの読み込みや、物を組み立てる変換は使わない(任意の処理が動く危険があるため)。
   - 上限: 文字列4000文字、札64枚、識別名40文字。超えたら読み込まない(超えた理由を返す)。
   - Godot の JSON は数字を小数で返すので、整数に直してから整える。
8. **知らない札は残したまま保存する**(使えない札)。新しい版で開き直せば元に戻る。
9. **未開放の札**が入っていたら、置けるが「未開放」と表示し、対戦では無視する。

### States and Transitions(状態と移り変わり)

ルールの形式そのものは状態を持たない「値」とする。

| 場面 | 持ち主 | 変更 |
| ---- | ---- | ---- |
| ルール盤の上 | 7 ルール盤 | できる(いつも整った形を保つ。重複は置く時点で置けない) |
| 対戦中 | 8 → 4 | できない(対戦を始めるときに写しを渡して固定する) |
| 保存したもの | 10・11 | 10 を通して上書きする |

### Interactions with Other Systems(他の仕組みとの関係)

| 相手 | 受け取るもの | 渡すもの |
| ---- | ---- | ---- |
| 2 ルール札の定義 | 識別名、調整値の名前・範囲・既定値 | — |
| 4 ルールの実行部分 | — | 整えた札の一覧(使えない札・未開放の札は除く) |
| 7 ルール盤 | 置く・外す・調整値の変更 | 札の一覧、使えない札の一覧 |
| 8 対戦の開始と席 | — | 固定した写し |
| 10 保存と名前付け | — | 決まった形の文字列、同じルールかどうかの判定 |
| 11 保存データ | 保存してある文字列 | 決まった形の文字列 |
| 9 特殊札・12 札の開放 | 追加された札(形は変わらない) | — |

**版を上げるとき**: 札が増えるだけなら版は上げない(知らない札の決まりで吸収する)。形そのものが変わるときだけ版を上げ、古い識別名から新しい識別名への置き換え表を持つ。廃止した識別名は使い回さない。

**技術判断の記録(ADR)に回すこと**: 保存の方法(`user://` にファイルとして書くか、ブラウザの保存機能を直接使うか、保存の確定をどう確かめるか)。4.7 でのブラウザ保存の振る舞いは、実際に書き出して確かめる。

## Formulas(計算式)

### 式1 調整値の整え

`整えた値 = 数として使えるなら 整数化(四捨五入(範囲内に丸める(x, 最小, 最大)))、使えないなら 既定値`

**変数:**

| 変数 | 型 | 範囲 | 意味 |
| ---- | ---- | ---- | ---- |
| x | 読み込んだ値 | 何でも入りうる | 保存データにある値 |
| 最小・最大・既定値 | 整数 | ルール札の定義のとおり | 例: `count` は 1〜2(既定 1) |
| 整えた値 | 整数 | 最小〜最大 | 実行部分に渡す値 |

- 「数として使える」のは有限の数だけ。文字列(`"2"` を含む)・真偽の値・null・非数・無限大は既定値にする。文字列から数への変換はしない。
- 範囲内に丸めるのを先に行う(1e300 のような値で桁があふれないように)。最小・最大が整数なので結果は順番に左右されない。
- 四捨五入は、ちょうど0.5のとき0から遠い方へ寄せる(Godot の round と同じ)。

**出力の範囲:** 必ず最小〜最大。
**例(`count` 1〜2):** 1.4→1、1.5→2、2.5→2、9→2、-0.5→1、0→1、1e300→2、"2"→1、null→1。
**例(`limit` 1〜5):** 5.49→5、5.5→5。

### 式2 上限の判定

`受け入れる = 文字数(文字列) ≤ 4000 かつ 要素の数(cards) + 要素の数(unusable_cards) ≤ 64 かつ すべての識別名で 文字数(識別名) ≤ 40`

**変数:**

| 変数 | 型 | 範囲 | 意味 |
| ---- | ---- | ---- | ---- |
| 文字数 | 整数 | 0以上 | 文字の数(バイト数ではない) |
| 要素の数 | 整数 | 0以上 | 整える前の数。壊れた要素と重複も数える |

- 文字数は JSON を解析する前に、残りは解析した後・整える前に確かめる。
- 書き出すときも、書き出した文字列の文字数が4000以下であることを確かめる(超えたら保存を断る)。

**出力:** 受け入れる/受け入れない(理由付き)。
**例:** 4000文字・64枚・40文字は受け入れ、4001文字・65枚・41文字は受け入れない。

### 定義 同じルールかどうか

- `同じ(A, B) = (決まった形(A) == 決まった形(B))`
- 必ず成り立つこと: `決まった形(読み込み(決まった形(x))) == 決まった形(x)`(何度書き出しても同じ)

## Edge Cases(特殊な場合)

### 読み込まず、理由を返すもの(異常終了はしない)

- **もし JSON として解析できない(空の文字列・途中で切れた文字列・入れ子が深すぎるものを含む)なら**: 読み込まない。理由「形が壊れている」。
- **もし最上位が対応表でない(並び・数・文字列)なら**: 読み込まない。理由「形が違う」。
- **もし format_version が無い・文字列・真偽の値・整数でない・1より小さいなら**: 読み込まない。理由「版が読めない」。ただし 1.0 は1として扱う。
- **もし今より新しい版なら**: 読み込まない。理由「新しい版で作られたルールです」。
- **もし古い版なら**: 版を移し替えてから整える。書き出すときは今の版になる。
- **もし上限(式2)を超えるなら**: 読み込まない。理由「長すぎる」(どの上限かを含める)。
- **もし cards(または unusable_cards)があるのに並びでないなら**: 読み込まない。理由「札の一覧の形が違う」。cards が無いときは0枚とする。

### その部分だけを外す・整えて、残りを読むもの

- **もし要素が対応表でない、id が無い・文字列でない・空の文字列なら**: その要素だけを捨て、捨てた数を返す(使えない札にも入れない)。
- **もし id が知らない識別名なら**: 使えない札へ移す。大文字・小文字は区別する(`Deal_All` は `deal_all` と別)。
- **もし最上位に決まった3項目以外の項目、要素に id と params 以外の項目があるなら**: 捨てる。
- **もし params が対応表でない(null・並び・数)なら**: 調整値が無いものとして既定値を入れる。
- **もし知らない名前の調整値なら**: 捨てる。
- **もし調整値を持たない札に params が付いているなら**: params ごと捨て、書き出しでも書かない。
- **もし使えない札に params が付いているなら**: 整えずにそのまま持つ。
- **もし unusable_cards の中に今の版で知っている識別名があるなら**: cards へ戻して調整値を整える(未開放なら「未開放」とする)。
- **整える順番**: cards の後ろに unusable_cards をつないだ1本の並びとして、基本の決まり4の手順2〜4を行う。
- **もし同じ識別名が cards と unusable_cards の両方にあるなら**: 前にある cards 側だけを残す。
- **もし同じ識別名で調整値の違う札が2枚あるなら**: 1枚目の調整値を使う。
- **もし JSON の対応表の中に同じ鍵が2つあるなら**: 解析器が後ろの値を採る。見分けられないため、仕様として受け入れる。

### 札の数

- **もし札が0枚なら**: 正しいルールとして扱い、`"cards":[]` と書き出す。
- **もし札が全部使えない札なら**: cards は0枚、unusable_cards に全部を残し、実行部分には0枚を渡す。
- **もし未開放の札しかないなら**: cards に全部を残し、実行部分には0枚を渡す。未開放の札も決まった形に含まれる。
- 実行部分に渡す札が0枚のとき、対戦を始められるかは 7 ルール盤と 8 対戦の開始と席が決める。

### 書き出しの形が崩れないようにする決まり

- 整数は小数点を付けずに書く(Godot は 3 を 3.0 と書き出すおそれがあるため)。
- 鍵は名前の順に並べ、空白は入れない。使えない札の調整値に小数があれば、精度を落とさずに書く。
- **もし書き出した文字列が4000文字を超えるなら**: 保存を断り、理由「長すぎる」を返す(既定値を省略しないため、読み込んだ文字列より長くなりうる)。
- ゲームの版が変わり、知らなかった札が知っている札になると決まった形も変わる。これは意図どおり。同じゲームの版の中では何度書き出しても同じ形になる。

## Dependencies(依存関係)

- **依存先**: 2 ルール札の定義(`design/gdd/rule-card-definition.md`、承認済み)— 識別名、調整値の名前・範囲・既定値
- **依存元**: 4 ルールの実行部分、7 ルール盤、8 対戦の開始と席、10 ルールの保存と名前付け、11 保存データ(いずれも未設計)
- **関係する側**: 9 特殊札、12 札の開放(札を足すが、形は変えない)
- これらの設計書を書くときは、この設計書への参照を必ず入れる(両方向の参照)。

## Tuning Knobs(調整できる値)

| 値 | 既定 | 安全な範囲 | 影響 |
| ---- | ---- | ---- | ---- |
| 文字列の上限 | 4000文字 | 2000〜8000 | 小さすぎると大きなルールを保存できない。大きすぎると悪意のある入力に弱い |
| 札の上限(使える札＋使えない札) | 64枚 | 32〜128 | 札の種類が増えたら見直す |
| 識別名の上限 | 40文字 | 32〜64 | 今の最長は `flow_clear_on_all_pass` の22文字 |
| 形式の版 | 1 | 上げるだけ | 形そのものが変わるときだけ上げる |

**決まり**: ルール札の調整値の範囲は広げるだけにする。狭めるときは形式の版を上げる(保存したルールの意味が黙って変わらないように)。

## Visual/Audio Requirements(見た目と音)

この仕組みには見た目と音の要件はない。

## UI Requirements(画面の要件)

表示は他の仕組みが受け持つ。この仕組みは表示のための情報を返すだけである。
- 使えない札・未開放の札の表示 → 7 ルール盤
- 読み込み・保存を断った理由の表示 → 10 保存と名前付け
- 理由は決まった種類で返す: 「形が壊れている」「形が違う」「版が読めない」「新しい版で作られたルールです」「長すぎる」「札の一覧の形が違う」、および捨てた要素の数

## Acceptance Criteria(合格の基準)

単体テストは `tests/unit/rule_format/`、結合テストは `tests/integration/rule_format/` に置く。札の定義と開放の状態は外から差し込み、ファイルの読み書きはしない。

### 自動の単体テスト

1. **GIVEN** 名前・作成日・人数の鍵を足した文字列、**WHEN** 読み込んで書き出す、**THEN** 最上位の鍵は `format_version`・`cards`・`unusable_cards` の3つだけ。(決まり1)
2. **GIVEN** 16枚の定義、**WHEN** 調整値の名前を集める、**THEN** `add_jokers`=`count`、`place_on_field`=`rank`、`lose_on_pass_limit`=`limit` で他の13枚は0個。共通の一覧とも一致する。(決まり2)
3. **GIVEN** 基本の決まり3の例、**WHEN** 読み込んで書き出し、解析し直す、**THEN** `cards` は要素3つの並び。(決まり3)
4. **GIVEN** `{"id":"foo_bar","params":{"x":1}}` を含む、**WHEN** 整える、**THEN** `unusable_cards` に原文のまま1件入り、実行部分に渡す一覧には入らない。(決まり4)
5. **GIVEN** `add_jokers` を count 2 → count 1 の順に2枚、**WHEN** 整える、**THEN** 1枚だけ残り count は2。(決まり4)
6. **GIVEN** `add_jokers` に調整値なし、`rank` 7.6、`limit` 9、`limit` 0、`add_jokers` に `speed`、`act_pass` に `count`、**WHEN** 整える、**THEN** それぞれ count 1、8、5、1、speed は消える、params は消える。(決まり4・式1)
7. **GIVEN** `"cards":[]`、**WHEN** 読み込む、**THEN** 失敗せず札は0枚。(決まり4)
8. **GIVEN** 版0の文字列とテスト用の置き換え表、**WHEN** 読み込む、**THEN** 版1の形になる。(決まり4)
9. **GIVEN** `deal_all`・`act_pass`・調整値なしの `add_jokers` の順に置いたルール、**WHEN** 書き出す、**THEN** `act_pass`・`add_jokers`・`deal_all` の順で `"count":1` が書かれる。(決まり5)
10. **GIVEN** 同じ札を逆の順に置いた2つと、count だけが1と2で違う2つ、**WHEN** 比べる、**THEN** 前者は「同じ」、後者は「違う」。(決まり6)
11. **GIVEN** 4000文字・64枚・40文字の入力と、4001文字・65枚・41文字の入力、**WHEN** 読み込む、**THEN** 前者は受け入れ、後者は理由「長すぎる」で断る。(決まり7・式2)
12. **GIVEN** 途中で切れた文字列、`"res://x.tres"` や物を組み立てる書き方を含む文字列、`count` 2.0、**WHEN** 読み込む、**THEN** 前者は理由「形が壊れている」を返して異常終了せず、結果に含まれる値は整数・文字列・並び・対応表だけで、2.0 は整数の2になる。(決まり7)
13. **GIVEN** 知らない札を含むルール、**WHEN** 書き出して読み込み直す、**THEN** `unusable_cards` は1文字も変わらない。その識別名を足した定義を差し込んで読むと `cards` に戻る。(決まり8)
14. **GIVEN** `cond_adjacent` を未開放にした状態、**WHEN** 読み込む、**THEN** 決まった形には残り、実行部分に渡す一覧には入らない。(決まり9)
15. **GIVEN** `format_version` 2 の文字列、**WHEN** 読み込む、**THEN** 理由「新しい版で作られたルールです」で断る。(特殊な場合)
16. **GIVEN** 書き出すと4001文字になるルール、**WHEN** 書き出す、**THEN** 理由「長すぎる」で保存を断る。(式2)
17. **GIVEN** 大富豪・7ならべ・ババ抜き、**WHEN** 書き出す→読み込む→書き出す、**THEN** 1回目と2回目の文字列が一致する。(定義)

### 結合テスト

18. **GIVEN** 対戦を始めて写しを渡した、**WHEN** ルール盤で `act_pass` を外し count を2にする、**THEN** 対戦側の写しの決まった形の文字列は開始時と1文字も変わらない。(状態)
19. **GIVEN** 大富豪(10枚)・7ならべ(8枚)・ババ抜き(6枚)、**WHEN** 書き出して読み込み、実行部分で4人×100局(乱数の種1〜100)回す、**THEN** 300局すべてが決着し、手数の上限で打ち切られた局は0局。(他の仕組みとの結合)

### 性能の測定(合否のテストとは分ける)

20. 札20枚(16種類＋知らない札4枚)のルールの読み込みと整えを100回行い、1回あたりの平均が1ミリ秒以内。ブラウザ版では手動で測る。

### 手動

21. ルール盤で、未開放の札に「未開放」の表示が出る(ルール盤の実装後に確かめる)。
